# V1.4 workbench design

User approved starting the proposed V1.4 home/basic projects/todos/notes on
2026-10-04. This document records implementation choices within that authorized
scope; it does not authorize another release. Codex and personal desktop tools
are the agreed direction; character raising/alternate AI providers are deferred.

## Outcome and interaction

A modeless native workbench opens from the Hub, tray and pet menu, without
hiding or changing the star ring. Home shows the existing accepted Codex task
set and local pending todos. Project selection filters user-owned todos/notes
and explicitly linked tasks. Projects have a name and optional folder. Todos
can be added, edited, completed, reopened, moved or deleted. Notes have titles
and plain-text bodies, with explicit Save/Ctrl+S and dirty-draft protection on
selection/close/application exit. Project deletion retains notes/todos in the
unassigned inbox. No samples are installed in the real store.

The workbench has a project sidebar and four clear tabs: Home, Todos, Notes,
Projects. Existing lavender/navy/pearl colors and system CJK/Segoe UI typography
carry the companion identity, with restrained celestial header artwork, readable
content surfaces and one clear primary action per tab. A splitter and scrollable
lists keep controls usable on smaller workareas. Keyboard focus and shortcuts
remain native. English/Chinese follow existing Settings; no translated draft is
lost when settings change. This is Windows desktop UI, not a new web application.

## Data and integration

`workbench_store.py` owns a separate local SQLite database under the existing
CodexWisp preference directory. Standard sqlite3 transactions, bound parameters,
foreign keys and schema_version protect local records. No new dependency. A
store is created lazily when the workbench is opened. Failed writes never clear
an editor draft or update UI as though saved; corrupt/future schemas fail without
replacing the existing file. Personal content stays outside Git and the package.

`workbench.py` owns widgets and user actions. `widget.Panel` lazily owns one
window/store and updates its task view from TaskPanelManager's already accepted
universe/page identities. No extra provider, filesystem crawler, chat reads,
microphone/keyboard worker or polling clock is introduced. Explicit manual task
links use stable (provider_id, task_key), never project-name guesses. Retired
tasks are absent from live task rows; stored links can survive to a later return.

The existing singleton/normal application remains unchanged. Non-live panels
and the dedicated synthetic preview use temporary stores. Preview exits close
all windows/stores and do not write personal settings or acquire the live lock.
APP_VERSION stays1.3.0; V1.4 preview/guide explicitly describes unreleased work.

## Acceptance

- Empty real store is useful; all CRUD actions persist across reopening.
- Project deletion unassigns todos/notes; foreign keys prevent orphan links.
- Notes preserve drafts through storage failure, navigation cancellation,
  language change and exit cancellation; Save/Discard/Cancel are explicit.
- Workbench reuses all accepted task identities, including off-page activation;
  no stale task/detail or ring visibility change on workbench show/hide.
- Real native dark/light captures, smaller workarea and both languages reviewed.
- Targeted storage/workbench/integration plus affected existing regressions pass.
- Isolated frozen package includes code/docs/licenses and excludes OpenCode;
  temporary-data and personal preference/lock boundaries verified.
- Finish at WAITING_FOR_HUMAN_VISUAL_QA; do not publish V1.4 automatically.
